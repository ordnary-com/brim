Backend code that is hard to get wrong

Brim is a small, statically typed language by Ordnary for command-line tools and backend services. It keeps Go's simplicity, compiles to native executables through LLVM, and makes the compiler catch what Go lets through.

server.brim
import std.http
import std.log

fn run(port: i64) -> Result[i64, string] {
    let server: http.Server = http.serve("127.0.0.1", port)?
    log.info("listening on port " + to_string(port))
    while true {
        let request: http.Request = server.next()?
        request.respond(http.text(200, "Hello from Brim!"))?
    }
}

fn main() {
    match run(8080) {
        Ok(_) => {}
        Err(e) => log.error(e)
    }
}

Why Brim

Keep what makes Go productive.
Design out what costs time.

Brim grew out of the bugs Ordnary kept fixing in Go services. Most of them come from Go's core design, so they cannot be fixed in Go itself.

Errors you cannot ignore

Errors are values: Result[T, E] with the ? operator to pass them up. No exceptions, and no _ to quietly throw one away.

No null

There is no nil. Absence is an explicit Option[T] that the compiler checks, so there are no nil pointer panics.

Real enums, exhaustive match

Enums carry data, and every match must cover every case, at every depth. Add a variant and the compiler lists each place to update.

Checked integers

Overflow never wraps silently. It stops the program with an error pointing at the exact expression, plus the call stack.

Immutable by default

Variables need let mut to change, and must be initialised. No implicit zero values hiding a forgotten field.

One type system, front to back

brim gen ts turns your API types into TypeScript, so renaming a field breaks the frontend build, not the browser.

A helpful compiler

Diagnostics that tell you what to do next.

Every diagnostic has a code, points at the source and usually says how to fix the problem. Forget a case and Brim names the value nobody handles.

  • Exhaustiveness checked for nested patterns and guards
  • Run-time errors show the call stack, with a stable R code
  • The same errors in your editor through brim lsp

    Low,

}
brim gen ts > api.ts
export interface Task {
  id: number;
  title: string;
  assignee: string | null;
}

export type Priority = "Low" | "High";

Backend and frontend

Declare API types once.

A Brim backend shares its API types with a TypeScript frontend. Every pub struct and enum becomes a TypeScript declaration, so a breaking change is a compile error on both sides.

  • Option[T] maps to T | null
  • Plain enums become string unions
  • Run it in CI to keep both sides in step

Batteries included

One command for everything.

Running, testing, formatting, dependencies and editor support all live in the brim command. Programs run on an interpreter while you work and compile to native executables when you ship.

brim run

Check a program and run it right away

brim build

Compile a native executable with LLVM

brim test

Run the tests, optionally filtered

brim fmt

One style, no options, for every program

brim new

Create a project with brim.toml

brim update

Update git dependencies in brim.lock

brim gen ts

Write TypeScript types for your API

brim lsp

Errors, hover and go to definition in your editor

brim check

Report errors without running anything
