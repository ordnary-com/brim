# Brim package registry

The service behind `brim publish` and registry dependencies (`http_router = "1.2"`
in `brim.toml`). It implements the protocol in [`docs/registry.md`](../docs/registry.md):
the JSON API under `/api/v1/`, plus two small HTML pages (`/` lists and searches
packages, `/packages/{name}` shows one).

It is a Cloudflare Worker written in TypeScript:

- **D1** (binding `DB`) holds the index: users, token hashes, packages and versions.
  The schema is in [`migrations/`](migrations/).
- **R2** (binding `ARCHIVES`) holds the archives, at `{name}/{name}-{version}.tar.gz`.
- The secret **`ADMIN_TOKEN`** guards `POST /api/v1/admin/tokens`.

| Path | What |
|------|------|
| `src/index.ts` | Routing and error handling |
| `src/api.ts` | The API endpoints |
| `src/archive.ts` | Archive checks (gzip, ustar entries, paths, `brim.toml`) |
| `src/semver.ts` | Versions, requirements and precedence |
| `src/auth.ts` | API and admin tokens |
| `src/pages.ts` | The HTML pages |
| `worker-configuration.d.ts` | Generated by `npm run types` from `wrangler.jsonc` |

## Deployment

The service runs at **https://registry.brimlang.com** (the default registry of
`brim`), in the Ordnary Cloudflare account: D1 database `brim-registry`, R2
bucket `brim-registry-archives`, and `registry.brimlang.com` as the Worker's
custom domain (`workers.dev` is off). Deploy with:

```sh
cd registry
npx wrangler d1 migrations apply brim-registry --remote   # when there are new migrations
npx wrangler deploy
```

## Local development

```sh
cd registry
npm ci
echo 'ADMIN_TOKEN=dev-admin-token' > .dev.vars   # not committed
npx wrangler d1 migrations apply brim-registry --local
npx wrangler dev                                 # or: npm run dev
```

Local D1 and R2 data lives in `.wrangler/`. Point `brim` at it with
`BRIM_REGISTRY=http://localhost:8787`.

Checks:

```sh
npm run typecheck
npm test
```

The tests run inside the Workers runtime (Vitest with `@cloudflare/vitest-plugin`)
against local D1 and R2, with the migrations applied in `test/apply-migrations.ts`.
After changing bindings in `wrangler.jsonc`, run `npm run types`.

## Creating a token

Until accounts come from Ordnary's identity service, publishers get a token from
the admin endpoint. It creates the user when it is new and prints the token once;
the registry keeps only its SHA-256.

```sh
curl -X POST https://registry.brimlang.com/api/v1/admin/tokens \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"user": "alice"}'
# {"token":"brim_..."}
```

The publisher then runs `brim login` and pastes it.

## Deploying

Do this once, from a machine logged in with `npx wrangler login`:

- [ ] Create the database: `npx wrangler d1 create brim-registry`, and put the
      printed `database_id` in `wrangler.jsonc` (it is a placeholder of zeros now).
- [ ] Create the bucket: `npx wrangler r2 bucket create brim-registry-archives`.
- [ ] Apply the migrations: `npx wrangler d1 migrations apply brim-registry --remote`.
- [ ] Set the admin token: `npx wrangler secret put ADMIN_TOKEN` (paste a long
      random value, for example from `openssl rand -base64 32`).
- [ ] Deploy: `npm run deploy`.
- [ ] Add a custom domain for the Worker (dashboard: Workers > brim-registry >
      Settings > Domains & Routes, or a `routes` entry with `custom_domain: true`
      in `wrangler.jsonc`), and make it the URL in
      `brim_package::registry::DEFAULT_REGISTRY`.
- [ ] Check it: `curl https://<registry>/api/v1/search` answers `{"packages":[]}`,
      then create a token as above.

Later schema changes: add a numbered file to `migrations/`, apply it with
`npx wrangler d1 migrations apply brim-registry --remote` before deploying the
code that needs it.
